## 1. 调研摘要与当前判断

香港开放数据可以支持的产品不只限于最初规划中的“商业名单查询与 CSV 导出”。本轮筛出五个主要方向：楼宇背景、购物格价、企业变更、食肆牌照及招标监控。真正可能产生价值的不是重复展示政府数据，而是围绕用户的一项决定，完成实体关联、跨源比较、变化解释与持续关注。

目前有较直接的数据证据支持进一步研究楼宇背景、购物清单格价和招标监控。企业与牌照名单也有结构化来源，但“名单变化能否带来有效商机”尚未验证。所有方向的付费意愿、竞争差异、持续运行成本和生产可用性均未确认；本文不承诺覆盖全港、不承诺实时预警，也不据此开始开发。

### 1.1 核心发现表

| 候选方向 | 已确认的数据基础 | 待验证的产品价值 | 核心边界 |
| --- | --- | --- | --- |
| 楼宇背景查询 | 楼宇资料、验楼通知和部分命令数据；验楼空间接口已读到实际样本 | 查楼前集中查阅；物业人员关注楼宇变化 | 楼宇级累计记录不等于逐张通知，也不构成安全判断 |
| 购物清单格价 | 消委会每日 JSON／CSV；已读到商品代码、多超市价格及优惠 | 一篮子比较、常买清单、降价提醒 | 缺少报价不等于缺货；优惠、运费与渠道差异不能忽略 |
| 企业变更情报 | 新成立／更名等周报；公司注册地址 API 已返回实际样本 | 企业基础资料核对、关注企业变化、新注册企业筛选 | 注册地址不一定是营业地点；注册不等于采购需求 |
| 食肆牌照变化 | 每日上午 9 点更新的持牌食肆名单，XML／空间数据入口 | 地区筛选、持牌查询、名单变化辅助拓客 | 名单新增不等于新开业，名单消失不等于结业 |
| 招标机会监控 | GLD XML 实际公告；DPO JSON 实际样本 | 减少漏看相关公告，追踪截止及重要变更 | 公告不等于完整标书；不能判断资格或保证不漏标 |

## 2. 背景、范围与证据等级

### 2.1 背景与当前决策状态

- 原始《产品需求与规划文档》列有商业牌照查询、导出、强检楼宇和招标监控。本轮调研允许超出该规划，重新选择有价值的功能。
- 讨论中曾形成“考虑 B 端收入、聚合与变化监控、先验证一个场景”的倾向，但后续重新开放了 C 端生活功能的比较；不能把该倾向视为全部候选功能的强制前提。
- **已定事项：** 先保存候选方向、来源地址与限制，再逐个分析。
- **未定事项：** 第一类用户、首个功能、收费方式、通知渠道、开发范围与上线时间。
- 本文仅新增调研记录，不修改现有 PRD，不改变 App 当前功能，也不替代后续需求或接口方案。

### 2.2 证据等级

| 标记 | 含义 | 不代表什么 |
| --- | --- | --- |
| E2：样本已读 | 已读取实际响应或字段结构，正文注明读取范围 | 不代表完整数据已下载、全量解析已完成或接口长期稳定 |
| E1：目录已核实 | 已在数据集页面、搜索结果或官方关联列表看到来源、格式或说明 | 不代表原始文件正文可读，也不代表字段语义已经确认 |
| E0：探索入口 | 只有提供方／分类入口或候选思路，尚未核实具体资源 | 不代表该功能所需数据确实开放 |
| 产品假设 | 对用户、使用频率、差异化或变现方式的推测 | 不代表用户调研或付费验证结果 |

本轮部分 CSV、PDF、DOCX 请求未返回可读正文。应记录为“入口已找到，正文待核实”，不能因此断言源文件为空、接口不可用或数据不存在。下文更新频率均指官方页面标称频率，不是服务等级承诺。

### 使用地址时的注意事项

1. 同时保留**数据集页面**与**原始资源地址**。原始地址失效时，先回目录查看是否迁移。
2. 目录的 `res.data.gov.hk/api/get-download-file?name=...` 是下载转发形式，不应直接当成业务查询接口。
3. `/en-datasets/provider/...` 中的提供方标识不能靠部门英文名缩写猜测。本轮曾出现错误标识返回泛列表的情况，必须检查页面是否真的应用了目标提供方筛选。
4. 本轮早期尝试的若干 CKAN 路径未成功，不应复制为已验证接口。
5. 页面有历史下载区域不等于具体时间段一定有文件；静态读取到“0 条”也不能证明无历史数据，须使用正式机制核实。

## 4. 方向一：楼宇背景查询与物业监控

### 4.1 用户问题与候选形态

**产品假设：** 买楼、租楼、接管物业或准备维修时，用户需要在多个官方页面查同一栋楼。将这些记录关联到楼宇实体，可能比再做一个楼龄查询更有价值。

| 潜在用户 | 要完成的决定／工作 | 候选输出 |
| --- | --- | --- |
| 买家、租客 | 看楼前需要进一步问业主／代理哪些问题 | 楼宇基本资料、已公开通知类别、来源及覆盖期 |
| 业主、法团、物业经理 | 所关注楼宇的公开记录是否发生变化 | 楼宇关注列表、数据变化摘要、核实入口 |
| 验楼、测量、维修服务企业 | 哪些楼宇值得进一步了解需求 | 地区与通知类别筛选；不是保证有订单的销售线索 |

候选最小闭环：**搜索地址 → 确认是哪一栋／哪一座 → 查看分源记录 → 阅读解释与官方原文 → 收藏关注。**

“买租前查询”与“物业多楼宇监控”是不同场景，不能仅因共用数据就默认一起做。

### 4.3 已看到的验楼字段与语义

| 字段 | 样本含义 | 产品处理注意 |
| --- | --- | --- |
| `BLOCK_ID_EN`／`BLOCK_ID_TC` | 楼宇编号 | 可作为候选关联键；跨源稳定性仍需验证 |
| `AddressEN`／`AddressTC` | 地址 | 样本中 TC 字段也出现英文地址，不保证每条有中文译名 |
| `Cum_MBIS_Notice_Issued_EN` | 发出通知累计数 | 样本为字符串；不是逐张通知对象 |
| `Cum_MBIS_Notice_CW_WD_SS_EN` | 已遵从／撤销／取代合并累计数 | 无法从合并值分辨三种状态 |
| `CSUID_EN`／`CSUID_TC` | 地址相关标识 | 样本出现逗号分隔的多个值，不能直接假设单值外键 |
| `Latitude`／`Longitude`、`geometry` | 地理位置 | 同一样本中属性坐标和 geometry 有小差异，需确定展示口径 |
| `LastUpdate` | 源记录更新时间 | 样本为非 ISO 日期文本；不是通知发出日期，日期格式和时区待核实 |

本轮样本的 `LastUpdate` 文本为 `7/9/2026 ...`；未确认日月排列前，不将其解释为某个确定日期，也不声称样本已更新至调研当日。

### 4.4 能做与不能做

**候选能力：** 分源楼宇档案、按类别查公开记录、来源解释、关注楼宇的累计数变化、维修历史案例浏览。

**不能直接成立的能力：**

- “该楼当前有多少张未完成通知”：发出与已处理来源覆盖期不同，又不是逐通知对应记录，不能直接相减。
- “这栋楼安全／没有违建”：未命中可能来自覆盖、地址关联或更新问题。
- “该楼已完成维修”：已遵从、撤销和取代合并，不等价于工程完成。
- “每户未来要缴多少钱”：历史维修案例不是该楼预算，工程范围与单位数也可能不可比。
- “及时发现刚发出的验楼令”：月更累计数据不能保证事件及时性或给出精确事件日期。

### 4.5 后续逐项分析重点

1. 先选买租用户还是物业人员；使用频率与商业模式会明显不同。
2. 用真实楼宇手工建立参考档案，检查地址、座数、block ID 和多标识的关联是否准确。
3. 用户看完公开累计记录后能采取什么行动？若仍要重新查全部官网，节省的工作可能不足。
4. 累计变化是否能提供有价值的提醒，还是只有背景查询价值？
5. 付费报告、物业多楼宇关注或专业服务展示仅为变现假设；需验证需求与用途合规，不预设收入。

## 5. 方向二：购物清单格价与降价提醒

### 5.1 用户问题与最小闭环

**产品假设：** 家庭采购者会重复购买一组商品，比单品搜价更需要知道“按我的清单，哪家超市的已知总价更低”“这次优惠是否适合买我需要的数量”。

候选最小闭环：**保存常买商品及数量 → 比较清单的已知报价 → 阅读缺项／优惠限制 → 前往官方购物渠道 → 下一次继续使用清单。**

候选扩展：商品关注、降价提醒、可比价格历史、单店与多店商品费用比较。分店导航、库存和订单能力没有从本轮价格样本得到支持。

| `cat1Name`／`cat2Name`／`cat3Name` | 三层分类文本 | 分类浏览；不保证存在独立分类 ID |

### 5.4 比较规则与边界

- **单店买齐总价**与**部分商品已知小计**必须分开，缺报价不能按零元计算。
- 无报价不代表缺货；数据没有证明分店库存。
- “逐项取最低价”的结果只是已知商品价格下界，不含交通、时间、运费和最低消费，不等于最优购买方案。
- 数量优惠应按用户所需数量解释；不能为了平均单价更低默认让用户买更多。
- 本轮样本没有提供可用于确认每条商品价格时效的字段；抓取时间与官方价格生效时间必须分开。
- 价格的线上／线下适用渠道、税费／运费口径、促销有效期和会员条件需继续核实。
- 历史价格需确认源商品代码、规格和渠道在比较期内可比；仅保存快照并不自动得到可信的“历史最低价”。

### 5.5 后续逐项分析重点

1. 官方格价已经解决哪些问题？购物清单是否真的减少了重复搜索？
2. 目标用户的常买清单在源数据中有多少可比较商品，而不只是有多少商品总数？
3. 优惠是否足够结构化，能否在不误导用户的前提下算清数量价？
4. 用户愿意维护清单、接收提醒吗？只有“觉得有用”不等于持续使用。
5. 免费引流、增值提醒或商业合作均为假设；本轮未确认联盟链接、分佣或直接购买接口。

### 8.3 DPO 实际结构与接入风险

英文响应顶层为 `eoi-rfi-rfp` 数组，实际样本将一个公告的 `topic`、`resource`、`date` 放在不同数组元素中，而不是每个元素有一整条公告。读取结果是标题、链接、日期依次出现的对象序列。

- 不能按普通“一元素一公告”方式直接解析。
- 是否允许稳定按顺序分组、如何处理缺失元素，要核对字典并检查更多样本。
- 已读列表样本有标题、链接和日期，没有证明提供截止时间；补齐截止可能要进一步访问详情页。
- 繁简英版本要关联成同一公告，不能当成三条采购机会。

### 8.4 变化与提醒边界

- 编号、部门及官方 URL 可作为去重线索，但跨来源一致性必须验证。
- 缩写、年份、URL 参数变化可能造成重复；不能直接按标题相等判断同标。
- 截止延期、撤回、标题修改、数量变化分别定义；缺少标书附件时不能承诺检测附件修订。
- 当前列表移除可能只是已截止，不应直接解释为取消采购。
- 截止时间需确认香港时间、日期格式和缺失值；抓取失败不得触发取消提醒。
- “与你关键词相关”不等于“你符合供应商资格”。资格、保证金、业绩要求和投标材料仍以标书及提供方为准。
- AI 摘要只能作为有来源的辅助解释，不能给出已符合资格、中标概率或投资回报保证。

### 8.5 后续逐项分析重点

1. 先选一个供应商类型，以真实公告检查误命中和漏命中，而不是先铺全部行业。
2. 用户现在通过哪些网站、邮件或服务找标？重复检查和漏看的成本是什么？
3. 聚合、筛选、重要变更、截止提醒中，哪一项能促使用户实际采取行动？
4. GLD 与 DPO 的重叠有多少，补充源是否增加真正相关的项目？
5. 订阅收费可作为假设；账号、推送、支付和团队协作均未在本文确认需要开发。

## 9. 备选方向与扩展线索

### 建议讨论顺序（尚未定案）

1. **楼宇背景：** 优先看跨源关联是否成立，再选择买租还是物业人群。

## 11. 共性风险与数据使用原则

### 11.1 商业使用与来源署名

已读取的平台条款：<https://data.gov.hk/en/terms-and-conditions>，页面版本为 1.2，标示最后更新 2025-05-26。

- 条款允许遵守条件后免费作商业及非商业使用，并要求标明数据来源、提供方知识产权及平台署名。
- 对准确、完整、可靠、及时等不作保证，提供方也可修改或停止供数。
- 外链网站有各自条款；不能用平台总条款覆盖所有来源用途、个人资料处理或直接营销问题。
- 消委会及市建局页面明确列明各自知识产权所有者，应保留对应署名。
- 高风险用途（安全、信用、医疗、资质、合规裁决）需要额外专业审核；免责声明不能替代正确的产品语义。

### 11.2 时效、历史与变化

- 同时区分源记录更新时间、数据覆盖期、抓取时间与首次观察时间。
- 只有“首次观察到变化”时，不把它写成“事件发生在今天”。
- 比较前确认本次下载完整、格式正常、记录量无异常；失败或局部返回不能生成新增／消失结论。
- 历史检索 API 的具体资源覆盖、保留时间和条款待核实；自存快照也要确认可存储及再展示。
- 历史字段修订、统计口径改变、ID 重置可能产生假变化，需在产品里显式解释。
- 标称每日／每月更新不等于每次拉取都会变化，也不等于有更新 SLA。

### 11.3 数据关联与国际化

- 稳定标识优先于名称和地址文本；地址匹配存在座、栋、综合体、别名和多标识问题。
- 模糊匹配应提供候选与不确定性，不把错误关联隐藏在确定的用户结论里。
- 繁简英字段可能缺失或在同一语言字段出现另一语言；不保证自动得到完整三语体验。
- ID、商品代码和公告编号必须保存原值；翻译后的文本不能作唯一标识。
- 如用 AI 做分类、摘要或解释，保留原文和出处，用户能区分源事实与机器推测。

### 11.4 当前不预设的实现

本文没有确认需要引入统一情报平台、队列、向量数据库、爬虫集群、支付或账号系统。即使采用后台拉取，更新调度、存储模式、限流与费用也应在选定场景后设计，不为了“以后可能接更多源”提前建设。

## 12. 逐项分析框架与后续记录

### 12.1 每个方向统一回答的问题

1. **用户是谁：** 只选一个主要角色，列出最近一次真实使用场景。
2. **要作什么决定：** 不用“看数据”作答案，明确用户接下来会比较、询问、联系或提交什么。
3. **当前如何解决：** 官网、搜索、人工表格、已有 App 或商业服务；记录实际流程。
4. **什么数据是必须的：** 哪些字段、覆盖、事件粒度和及时性不可缺；哪些只是锦上添花。
5. **样本能支持到哪：** 逐项列出源事实、可计算结果、需要核实和无法判断的结论。
6. **相比现有方案改进什么：** 减少哪一步重复工作、降低哪类误读，是否促成实际行动。
7. **用户会重复使用吗：** 一次性报告和持续关注分开评价。
8. **谁愿意为什么付费：** 收费对象、交付内容和免费替代；不以下载量或口头好评替代证据。
9. **风险能否控制：** 地址误配、数据缺失、历史覆盖、用途限制和专业责任是否会破坏价值。
10. **本轮决定是什么：** 继续、收窄、补证据或暂缓；形成小范围结论，而不是立即承诺完整开发。
